# Engine — Feature Dispatchers

> **19/10/2026 — the per-representation model is gone (overhaul, decision Q2 bis).** `RepInScene`, `ViewScene`, `SceneRegistry`, the activator, the legacy visibility and active-array dispatch, the slice / clip planes and the `FESPP_BLOCKSCOPE` flag were removed: each view draws through its composite scene (`engine/blockscope`), a cut or filtered grid through its `GridIsolate`. A passage below that still names them describes removed code.

## Overview

The `fespp_on_trame/engine/*_dispatch.py` modules (plus a few non-`_dispatch` siblings: `property_values.py`, `trajectory_sampling.py`, `time_realization.py`, `compare_matrix.py`, `diff.py`, `etp.py`, `vtk_log.py`) are the **logic layer extracted out of `boot.initialize_fespp_engine`**. The pattern is uniform and important to internalize before forking: every function here is a **free function that receives all of its dependencies explicitly** (`state`, `controller`, `scene_registry`, `source_registry`, `view`, `tree`, …). `boot.py` registers thin `@state.change` / `@controller.set` closure wrappers that capture those deps from the engine-init scope and forward into these functions. Consequently, none of these modules import the engine wiring; they are oblivious to how they are invoked. When forking, expect to trace any handler back to a closure in `boot.py` to discover its real call site.

A second cross-cutting theme is the **legacy-vs-per-view duality** introduced across "Phases" (Phase 2 = single shared pipeline; Phase 3a/3b = per-`(rep, view)` pipelines owned by a `SceneRegistry`). Most slicer/slice/clip/threshold dispatchers first try to route an edit through `scene_registry.get_rep(view_id, rep_path)` (a `RepInScene`, which may delegate to a per-view `IjkGrid`), and only fall back to the shared `source_registry` when the scene registry isn't ready (early boot) or the rep hasn't been synced yet. The "target view" for an edit is resolved via a consistent precedence: `state.drawer_target_view_id` (the Attributes-drawer picker, "Brique A") → `state.fespp_active_panel_id` (active focus) → first known scene. Renders are pushed to the browser via `controller.view_update_for(panel_id)` (specific panel, pinned-mode safe) and `controller.view_update()` (legacy active panel) — usually both, because the cost of a no-op push is negligible.

> **⚠️ Refactor update (`refactoring` branch).** That target-view precedence, the `(panel, active rep)` lookup, the panel pv_view resolution, and the render + dual-push were previously copy-pasted across `slicer` / `slice` / `clip` / `threshold` dispatch. They now live in **`engine/view_routing.py`** (`target_panel_id(state, scene_registry=None)` — 3-tier with a registry, 2-tier without; `resolve_rep`; `scene_pv_view`; `render_and_push` / `push_to_clients`; and `resolve_active_render_panel(state, raw_id=None)` — coerces a panel id to a RENDER panel: with a stats/distribution tab focused, the raw active id points at a non-render panel and colour/visibility buckets written under it are silently lost; the coercion prefers the 3D view the user last worked in (`fespp_last_render_panel_id`, written by `MultiView._set_active`) over the first one; `panel_resolver.active_panel_id` and every load-time bucket write in `data_load` route through this coercion). The four dispatchers delegate, keeping only their own pv_view nuance — so the per-file descriptions below that re-explain this resolution reflect the pre-refactor copies. The stats/distribution/compare cluster (`stats_dispatch`, `distribution_dispatch`, `compare_matrix`) is property-driven ("Brique B") rather than view-driven, and builds transient PV filter chains that must snapshot/restore the PV active source + active view so the main render path never sees a transient proxy.

**Outputs that hold together (2026-09-11).** Three utility modules under `engine/utils/` (detailed in [[Core, IO & Utils|Core-IO-and-Utils]]) are what every dispatcher on this page now writes its numbers, names and files through; the rules, restated once here so a reader of a dispatcher does not have to leave the page:

- **`numfmt` — one number on screen.** `fmt(v)` = a measured quantity: FOUR significant digits (ties away from zero on the exact binary value), scientific notation when the ROUNDED value leaves `[1e-3, 1e6]` (`1.2e-14`, `3.4e+12`, no zero-padded exponent), thousands grouped by a THIN space (`1 235`, `1 000 000`), a point as the decimal separator (never a comma), an en dash `–` for a missing value (`None`, NaN, an empty string), `∞` / `-∞`. `fmt_int(v)` = a count, every digit, grouped, never scientific. `fmt_pct(fraction)` = `12.35 %`. `fmt_fixed(v, decimals)` = coordinates, depths, contacts. `unit_power(uom, power)` = `m3/m3`, `(m3/m3)²`, ASCII `(m3/m3)^2` for a CSV header; the power each descriptive statistic carries (variance 2, M3 3, M4 4; counts, skewness, kurtosis 0) is `STAT_UNIT_POWER` in `widgets/_shared/numfmt.js`, where the matrix is written. A category code is an IDENTIFIER, not a quantity: `str(int(code))`, ungrouped. The same rule, same worked examples, is `widgets/_shared/numfmt.js` (`fmt`, `fmtInt`, `fmtPct`, `fmtFixed`, `fmtPlain` — ungrouped, for an editable input — `parseNum`, `unitPower`), imported by every widget; `widgets/lint.sh` lints `_shared` too. Where it applies: the matrix of the Statistics view (written in the browser, unit in the `th`), Volumetrics, Log ↔ Grid, Data health counts, the well-log zones table, the Colormap card's labels and alpha readouts, the Attributes card, the calculator's chips and status line, the pick readout and cursor coordinates, the histogram NaN badge, the cross-plot lasso count, the health `range` messages and `utm_sanity`. Outside it, on purpose: Plotly tick labels (charts), the 3D colour bar (ParaView's own `%.4g`), file sizes in the upload dialog, the harness logs. Nothing is computed differently: the rule changes how a value is READ, never its value.
- **`categories` — names behind codes.** `labels_for(tree, array_path, vtk_name, reader) -> {code: name}` for a `CategoricalProperty` only (a `DiscreteProperty` such as drogon's `Facies` has no names: its codes show, and that is correct): the file's StringTableLookup through the fesapi channel first, then the LUT annotations FESPP wrote on the array; `{}` for a derived path or an unknown node. `label_of(labels, code)` = the name, else the code. `labels_note(...)` = the sentence a panel shows when a categorical property's names could NOT be read (`category names not readable for this property: its codes are shown`) — nothing silent. Consumers: the Thresholds card, the cross-plot legend, the histogram's discrete axis (`tickvals` / `ticktext`, `meta.categories`), the Volumetrics `region` column (`region_code` beside it).
- **`csv_export` — a file says where it comes from.** Every CSV opens with a comment block — `# fespp-on-trame <version> - <kind>`, `# date: YYYY-MM-DD HH:MM`, one `# key: value` per provenance field (property, unit, representation, realization, time step, picks, contacts, convention…), `# n/a = not available` last — then the column line with the unit named ONCE per column (`min (m3/m3)`, `variance ((m3/m3)^2)`, `GRV (m3)`, `cells`), then RAW values: the shortest round-trip decimal (`repr`, never the rounded or converted figure on screen), an int's full digits, `true` / `false`, `n/a` for a value that could not be evaluated, an empty cell for one that does not apply, text quoted when it holds a comma, a quote or a newline. Names are dated and server-decided: `<kind>_<slug>_<YYYY-MM-DD>.csv` (`statistics_2026-09-11.csv`, `volumetrics_Geogrid_…`, `distribution_…`, `health_…`, `log_grid_…`, `zones_<well>_…`). The two Vuetify panels get the whole text (`stats_dispatch.export_csv`, `distribution_dispatch.csv_for` → `utils.download`); a widget gets `{name, header}` and writes its rows raw from its props through `widgets/_shared/csvexport.js` (`buildCsv`, the one `handOver`: clipboard when the browser offers one, else a download, the button saying `Copied` / `Downloaded` / `Export failed — select the table and copy it`); Health and Log ↔ Grid add the one JS-authored line `# rows: as filtered (/sorted) on screen`. The XML copy stays verbatim.

What each dispatcher does with them is in its own section below: the **range checks** of `health_dispatch` (`expected_domain`, `range_findings`, the per-representation "not range-checked" info), the Colormap card's **Symmetric around 0 / Diverging** (`cmap_rescale`, under *The cards name their target*) and the **difference role** of `derived_props` read by the histogram and the Statistics view's distributions, the **Statistics export** (`compare_dispatch.csv_payload`) and the **zones export** (`welllog_dispatch.zones_csv_payload`), the Volumetrics / Statistics / Health / Log ↔ Grid payloads. **Harness additions.** `welllog_probe` logs `zones csv: name=… header=<n> lines`; `volumetrics_probe` logs every row with its `region_code`, then `volumetrics csv: name=… header=<n> lines` and the provenance lines themselves; `file_health` on drogon must list `('info', 'range')` in its by-category line (no warning: drogon has no time-series / multi-realization node, the only ones FESPP writes bounds on). Browser specs `09-exports`, `11-numbers`, `12-categories` (skipped out loud without `FESPP_SMOKE_CATEGORY`), `13-zones-export`, `14-compare-export` — see `tests/browser/README.md`. Unit: `test_numfmt.py`, `test_csv_export.py`, `test_categories.py`, `test_derived_role.py`, and the additions to `test_health.py`, `test_volumetrics.py`, `test_distribution_norm.py`, `test_crossplot_figures.py`, `test_compare_dispatch.py`, `test_reconcile.py`, `test_zone_stats.py`.

### `fespp_on_trame/engine/threshold_dispatch.py`

**Responsibility.** Threshold-chain dispatch routing both IjkGrid and non-IjkGrid (UnstructuredGrid) ops through `SceneRegistry` per `(view, rep)`. Publishes the active chain into `ui_threshold_chain` (depth-decorated + DFS-reordered) and forwards UI add/delete/set_range/set_visible events. Handles the multi-realization VTK-array-name resolution.

**Key classes / functions.**
- `_render_and_push(state, controller, fallback_view)` — local copy of the slicer helper (deliberately not imported from the sibling) resolving the target panel's `pv_view`.
- `_active_view_id(state)` — `drawer_target_view_id` → `fespp_active_panel_id`.
- `_find_property_path_by_title(tree, rep_path, array_title)` — walks the rep subtree for a property node whose (sanitized via `make_valid_vtk_name`) title or `propTitle` (for MR nodes) matches; returns the tree path. Recognizes node kinds containing `"Property"` plus `TimeSeries`/`MultiRealization`/`MultiRealizationTimeSeries`.
- `_resolve_vtk_array_name(state, tree, view_id, rep_path, array_title)` — **the MR-suffixing resolver.** Maps `state.active_color_array_name` (a property TITLE, e.g. `"VOIL"`) to the actual VTK array. For non-MR returns the sanitized title; for MR returns `<sanitized_title>_real_<idx>` where `idx` comes from `realization_dispatch.get_active_realization_for_view`. If MR but no realization picked yet, auto-picks `default_realization_for` AND persists it via `set_active_realization_for_view`. Falls back to the eye-binding's `ui_active_array_by_rep_by_view[view][rep]` array_path when the title walk misses.
- `threshold_provider(state, scene_registry, source_registry, view_id=None)` → `(provider, rep_path)`. For `rep_type in ("IjkGrid", "UnstructuredGrid")` prefers `scene_registry.get_rep(vid, grid_path)` (a `RepInScene`). If the scene **exists** but the rep isn't synced yet, returns `(None, None)` (publishes an empty chain silently, no legacy fallback, no `[DEPRECATED]` print). Otherwise falls back to `source_registry.get_ijk_grid` or `source_registry` itself.
- `hide_unused_scalar_bars()` — compat shim delegating to `source_resolver.hide_unused_scalar_bars`.
- `_is_per_view_provider(provider)` — `True` unless the provider has a `get_ijk_grid` attribute (i.e. `SourceRegistry` is the only legacy provider; its compat methods take `rep_path` first).
- `publish_threshold_chain(...)` — gets `provider.get_chain()` (or `get_chain(rep_path)` for legacy), computes `_depth` per entry from `parent_name`, then DFS-reorders so each child emits right after its parent's subtree; writes `state.ui_threshold_chain`. **Idempotent.**
- `refresh_threshold_ui_for_active_grid(...)` — **bails early** (clearing `ui_threshold_chain` + `ui_threshold_arrays_available`) when `state.fespp_data_selectors` is empty, then republishes arrays + chain.
- `chain_entries_for_property(state, scene_registry, source_registry, tree, prop_node_id, isolates=None)` — `[(view_id, entry_name), ...]` of the threshold entries fed by a property node, across every view's chain of its grid (matches the sanitized base array name and its MR `_real_<idx>` variants; `view_id=None` for the legacy single-registry provider). `isolates` is the live table of per-view grid isolates (`ctx.grid_isolates`, keyed `(view_id, rep_path)`): under BlockScope the chain lives there and nowhere else. Powers the unselect guard: `tree_views._threshold_refs_for` asks it whether anything still reads the property — over the isolates of LIVE views only (`per_view_state.is_live`), and `boot.on_panel_closed` drops a closed view's isolates (`_drop_isolates`, the isolate half of `_release_isolates`) — and the amber snackbar says how many entries, in which view (the tab titles from `fespp_render_panels`, never an id) and in whose Thresholds card to delete them.
- `threshold_add(state, controller, scene_registry, source_registry, activator, view, parent_name=None, array=None, view_id=None, tree=None)` — defaults `array` to `state.ui_active_node_reservoir_array_name` (the reservoir-scoped active property, immune to well/surface activations) falling back to `state.active_color_array_name`, runs MR resolution when `tree` is passed, calls `provider.add_threshold(...)`, republishes, refreshes the activator, hides unused scalar bars, renders.
- `sync_blocked_wellbore_chains(scene_registry, provider, rep_path, view_id)` — mirrors the grid's threshold chain onto its LOADED BlockedWellbores, the well-side twin of the colour mirror: FESPP puts the grid's CELL arrays on every loaded wellbore (same names, crossed-cells subset), so the grid's ranges apply verbatim and the wells keep only matching cells. Declarative reconcile — replays the grid's `snapshot_threshold_chain()` through `apply_threshold_chain` (full replace, idempotent) on each wellbore `RepInScene`, so all four ops reduce to the same call. Hooked into `threshold_add` / `threshold_delete` / `threshold_set_range` / `threshold_set_visible`, into boot's single-rep threshold copy-from-view, and into `data_load`'s fresh-wellbore block (a BW checked after the filter was set inherits the chain). Guards: only wellbores with an EXISTING per-view rep (an unchecked one is never materialised); no-ops on legacy providers (no `scene` attribute). Cost: one proxy teardown+rebuild per (loaded BW, entry) per op.
- `threshold_delete` / `threshold_set_range` / `threshold_set_visible` — forward to the provider's `delete_threshold` / `set_range` / `set_visible` (with the per-view-vs-legacy `rep_path` asymmetry), republish, render.
- `on_threshold_pending_action(state, action, threshold_add, threshold_delete, threshold_set_range, threshold_set_visible)` — single-entry-point dispatcher: reads `action["action"]` (`add`/`delete`/`set_range`/`set_visible`), calls the matching passed-in controller closure, then **clears `state.ui_threshold_pending_action`** in a `finally` (so identical repeat actions still fire past Trame's no-op-write collapse).

**State.** Writes `ui_threshold_chain`, `ui_threshold_arrays_available`, `ui_threshold_pending_action` (cleared). Reads `ui_active_node_reservoir_type_rep`, `ui_active_node_reservoir_rep_path`, `ui_active_node_reservoir_array_name`, `active_representation_path`, `active_color_array_name`, `fespp_data_selectors`, `ui_active_array_by_rep_by_view`, `drawer_target_view_id`, `fespp_active_panel_id`. Also reads/writes `ui_active_realization_by_array_by_view` indirectly via `realization_dispatch`.

**Collaborators.** `realization_dispatch` (MR detection + suffixing), `make_valid_vtk_name`, `source_resolver.hide_unused_scalar_bars`, `paraview.simple`. Providers: `RepInScene` (per-view, including its `_ijk_provider()` delegation for IjkGrid) and `SourceRegistry` (legacy). Entry points are boot.py closures; `on_threshold_pending_action` is the UI's funnel.

**Gotchas.**
- **The MR title-vs-array trap.** `state.active_color_array_name` carries the property **title**, not the VTK array name. For MR properties the real array is `<title>_real_<idx>`. Without `_resolve_vtk_array_name`, `RepInScene._add_threshold_local` fails at `_resolve_assoc(title)` and the threshold silently never appears (the 2026-05-27 smoke-test bug). `threshold_add` only runs the resolver when `tree` is passed — callers MUST pass `tree` or MR thresholds silently miss.
- `_find_property_path_by_title` was added because the old `ui_active_array_by_rep_by_view` bucket only tracks eye clicks; tree-activating a new property without an eye click left a stale path → MR suffixing with the wrong realization idx → a nonexistent array name.
- `refresh_threshold_ui_for_active_grid`'s early bail is a **segfault guard**: reading a provider after `source_registry.sync` Delete()'d the underlying PV source crashes inside `vtkPVRenderView` with no Python traceback.
- The uniform provider call convention (`provider.<op>(name/parent/...)`, no `rep_path`) collapses the dispatcher branching to "per-view provider vs legacy `SourceRegistry`" — detected solely by `_is_per_view_provider`.

### `fespp_on_trame/engine/realization_dispatch.py`

**Responsibility.** Per-view multi-realization choice — owns `state.ui_active_realization_by_array_by_view` and derives the per-panel / global realization-picker specs. Orthogonal to `active_array.py` (which owns the property choice). No reconcile with the plugin: loading is handled by tree selection; the picker only drives ColorBy.

**Key classes / functions.**
- `_MR_TYPES = frozenset({"MultiRealization", "MultiRealizationTimeSeries"})` — module constant.
- `is_multirealization_property(tree, array_path) -> bool` — `True` iff the node type is in `_MR_TYPES`.
- `available_realization_indices(tree, array_path) -> list[int]` — parses the node's `realization_indices` CSV attribute into a sorted int list (skipping non-ints).
- `default_realization_for(state, tree, array_path) -> Optional[int]` — the smallest available index (no global cursor anymore).
- `set_active_realization_for_view(state, panel_id, array_path, idx)` / `clear_active_realization_for_view(...) -> bool` / `get_active_realization_for_view(...) -> Optional[int]` — get/set/clear into the nested map `ui_active_realization_by_array_by_view[panel_id][array_path]`. The setter/clearer rebuild the dicts top-down (fresh inner dicts) so trame's state sync picks up the mutation.
- `suffixed_array_name(base_array_name, idx) -> str` — the single source of truth for the naming convention: `f"{base}_real_{idx}"`.
- `recompute_panel_has_mr(state) -> dict` — `{panel_id: bool}` from `ui_panel_active_mr_specs_by_id` (a panel has MR iff its spec list is non-empty).
- `recompute_global_mr_specs(state) -> list` — aggregates per-panel specs by `array_path`, taking the **union** of available indices, computing `current_idx` as the **mode** across panels, and setting `mixed=True` when panels disagree. Sorted alphabetically by title.
- `resolve_global_selected(state) -> tuple` — validates `ui_global_mr_selected_path` against `ui_global_mr_specs`; falls back to the first spec when stale; returns `("", None)` when no MR property exists.
- `recompute_panel_mr_specs(state, tree) -> dict` — builds `{panel_id: [{array_path, title, available_indices, current_idx}]}` from `ui_active_array_by_rep_by_view` (skipping non-MR / no-available-index paths, deduping by path). Title comes from `propTitle` → tree title → last path segment; specs sorted by title.

**State.** Writes `ui_active_realization_by_array_by_view`. Reads it plus `ui_panel_active_mr_specs_by_id`, `ui_global_mr_specs`, `ui_global_mr_selected_path`, `ui_active_array_by_rep_by_view`. The `recompute_*`/`resolve_*` functions return new values and **leave the write-back to the caller**.

**Collaborators.** The engine `Tree` API (`find_node_id`, `find_type`, `find_attribute_value`, `find_title`). Consumed by `threshold_dispatch._resolve_vtk_array_name`, `stats_dispatch`, `distribution_dispatch`, and the per-view/global RealizationPicker UI (via boot.py closures).

**Gotchas.** All map mutators rebuild dicts top-down because trame's state sync sometimes drops mutations through shared inner references (a recurring pattern across this codebase). The "global" picker reconciles divergent panels by taking the union of available indices and the mode of current indices, surfacing disagreement via the `mixed` flag. There is intentionally **no global realization cursor** anymore — the choice is strictly per-`(view, array_path)`.

### `fespp_on_trame/engine/distribution_dispatch.py`

**Responsibility.** Compute a Plotly histogram `Figure` for one row of the Statistics view. Replaces the noNaN-Threshold→DescriptiveStatistics chain with a single `numpy.histogram` (continuous) or `np.unique` (discrete/categorical) on the raw VTK array, pushing only a small binned trace over the WebSocket.

**Key classes / functions.**
- Constants: `_DEFAULT_NBINS=50`; display modes `_MODE_BARS/_LINE/_CURVE` (`_VALID_MODES`); norms `_NORM_COUNT/_DENSITY/_PROBABILITY` (`_VALID_NORMS`); `_DEFAULTS` dict; `_COLORWAY` (10-color Vuetify-aligned palette).
- `_numpy_imports()` / `_go_imports()` — **lazy** imports of numpy/`vtk_to_numpy` and `plotly.graph_objects` so engine boot survives a stale venv missing these.
- `_get_named_array(source, vtk_name)` — `UpdatePipeline` + locate the array by name on Cell/Point/FieldData.
- `_is_discrete_kind(prop_kind)` — `True` if the kind string contains `"discrete"` or `"categorical"`.
- `_apply_norm(counts, total, widths, norm)` — density = `counts/(total*widths)`; probability = `counts/total`; else raw.
- `_shape_trace_for_mode(centers, heights, widths, mode, color)` — builds the Plotly trace dict (bar / `scatter` step `shape="hv"` / `scatter` spline `shape="spline"` with fill).
- `_build_continuous_trace(...)` / `_build_discrete_trace(...)` — drop NaN pre-binning, optionally `np.cumsum` then `_apply_norm`; return `(trace, kept_count, finite_values, bin_centers, bin_heights, bin_widths)`.
- `_stats_overlay_shapes(np, finite_values)` / `_stats_overlay_annotations(np, finite_values)` — paper-anchored vertical lines + labels for Q1/median/mean/Q3. The labels (**2026-09-15**) are laid on two rows, alternating (`yshift` 12 px), and two lines closer than 4 % of the value span share one label (`med · mean`; a constant distribution gives one label for the four): they used to sit on one line at the same height, and a tight distribution drew them over each other. The `log_y` argument went with it — the labels are in paper coordinates and never read it.
- `_resolve_options(**kwargs)` — merges caller kwargs over `_DEFAULTS`, validating mode/norm and clamping `nbins` to `1..500`.
- `compute_histogram_figure(state, tree, source_registry, array_path, row_kind, row_id, *, nbins, display_mode, log_y, show_stats, cumulative, norm, real_idx=None, ts_idx=None, return_meta=False)` — the main per-row compute. `row_kind` ∈ {`"original"`, `"view"`, `"part"`}; `row_id` is `"default"` (original), the panel id (view) or the part's path (part). `real_idx`, `ts_idx`: the realization and the time step an original or a part's row reads, the ones its context names (`ui_distribution_contexts[<pid>]`, from `compare_set("dist", ...)`); naming none, the default realization and the session's current time. Resolves the source (a view's row through `drawn_cells.values` on what `stats_dispatch._resolve_rendered_inputs` says it draws, at the view's active realization + `ViewTime`, a formula's array among them: that row never reads the whole grid; an original row via `stats_dispatch._original_source_and_name`; a part's through `stats_supports.part_values`), reads the array, builds the trace, and returns a `go.Figure` (or `(fig, meta)` when `return_meta=True`). The chart's title: `<property>`, `<property> On <view>` or `<property> on <part>`, then `(real N, <time step>)` when relevant.
- `csv_for(meta, context) -> {name, text}` (2026-09-11) — the bins as a CSV through `csv_export`: provenance header (property, unit, representation, realization / time step, source kind and view, normalisation, cumulative, bins, component), columns `center (uom),[label,]<count|density|probability|cumulative …>,width (uom)` — the `label` column only when `meta["categories"]` is non-empty — raw values (a count height and a discrete centre written as integers: `170030`, `2`, never `170030.0` — a count is whole and a code is an identifier; a density keeps its decimals), a `# categories:` line when the names could not be read (`meta["categories_note"]`), name `distribution_<title slug>_<date>.csv`; `context` is built in `boot._refresh_distribution` from the resolved row. Replaces the former three-column text with no header. The panel's state `ui_distribution_csv_<pid>` holds `{name, text}` (never null) and its button hands both to `utils.download`; `ui_distribution_meta_<pid>.text` is the NaN badge's line (`kept / total  (n NaN)`, counts by `numfmt.fmt_int`), built here so the panel template formats nothing.
- **Category labels and differences (2026-09-11).** A discrete property's axis keeps the property name and unit (`xaxis_value_label`) and, when `categories.labels_for` names the codes (a `CategoricalProperty`), draws them as `tickvals` / `ticktext`; `meta["categories"] = [{value, label}]` is always present for a discrete property (`[]` for a continuous one). When `derived_props.is_difference(array_path)` (a property born of the calculator's `calc_diff`), the figure is a DIVERGING one: `xaxis.range = [-m, m]` with `m = max(|min|, |max|)` of the finite values, a dashed black zero line (`layout.shapes`), and in bars mode `diverging_colors(centers, widths)` — a bin wholly below 0 `DIVERGING_NEG`, wholly above `DIVERGING_POS`, straddling `DIVERGING_ZERO` (`_shape_trace_for_mode(..., colors=…)`); line / curve modes get the range and the zero line only; `meta["difference"]` says so. This is a FIGURE rule: a formula's 3D eye (`engine/derived_arrays`) colours its grid on the data's range, not a diverging one; the Colormap card's `Diverging` shortcut is the way for a file-borne difference. Binning untouched.

Overlaying SEVERAL rows in one histogram is not here: this module computes ONE row of ONE property per panel. The Statistics view builds its own overlay in `compare_dispatch.dist_figure` (cycling the `_COLORWAY` of this module).

**State.** Reads `fespp_render_panels`, and (via `realization_dispatch`) `ui_active_realization_by_array_by_view`. Writes none directly — returns figures/CSV to the caller.

**Collaborators.** `drawn_cells`, `stats_dispatch` (heavily: `_resolve_rendered_inputs`, `_title_and_kind`, `_prop_kind_for_array_path`, `_rep_path_for_array_path`, `_resolve_vtk_name`, `_original_source_and_name`, `_default_real_idx`, `_ts_label_for_idx`, `_unit_for_array_path`), `stats_supports.part_values`, `realization_dispatch`, `time_realization.label_for_time_value`, lazy numpy/plotly, `paraview.simple`. Consumed by the distribution panel via boot.py closures.

**Gotchas.**
- **PV-globals snapshot/restore.** `compute_histogram_figure` snapshots `GetActiveSource()`/`GetActiveView()` on entry and restores them in a `finally`, plus deletes any `owns_merged` AppendDatasets and calls `_restore_channel()` — so a transient merge or a mid-function exception cannot leak its active source/view into the main render path (which would trigger fan-out handlers on the wrong proxy).
- **Time handling differs by row kind.** An original row at a time step temporarily moves `TimeKeeper.Time` to the `ts_idx` it names (restored in `finally`, re-executing the source at the restored time); a part's row reads through `part_values`, which reads the grid's values at that step; a view's row reads the authoritative `pv_view.ViewTime`.
- Wellbore-channel arrays live only on the per-view extractor and are raw-named — `_orig_real_name` overrides `vtk_name` accordingly.

### `fespp_on_trame/engine/stats_dispatch.py`

**Responsibility.** The statistics of a property, as the Statistics view reads them (`compare_dispatch`, `compare_rows`): the VTK and numpy primitives of a read, the row of what a 3D view draws, what a row's weights have to say. It publishes nothing and holds no state: the rows of the view are `compare_dispatch.rows_for`'s.

**Key classes / functions.**
- VTK plumbing: `_resolve_rendered_inputs(rep_path, view_id)` (`(what the view draws of the grid, pv_view)`, `drawn_cells.Drawn` each: what its isolate shows, else what its composite keeps of a cut scene; empty when the view shows the whole grid), `_resolve_assoc(source, array_name)` ("CELLS"/"POINTS"), `_table_row_to_dict`, `_total_count_for_assoc`.
- **`transient_chain()`** — the context manager every read that builds proxies runs in: active source and active view saved, `SetActiveView(None)`, `vtkObject.GlobalWarningDisplayOff()`, all restored in `finally`. Each transient `Threshold` / `DescriptiveStatistics` calls `SetActiveSource(self)`; deleting them leaves the active source dangling, and the active-source change would otherwise be treated as user navigation (re-running `apply_color_array`, wiring a scalar bar). The warning toggle silences the expected "No active view found" spam during that window.
- `_compute_one_variable(input_source, array_name)` — the core compute of a view's row: `Threshold(Between -1e308..+1e308)` (drops NaN, since any NaN comparison is False) → `DescriptiveStatistics`, reads primary+derived blocks, adds `P10`/`Q1`/`Median`/`Q3`/`P90` via numpy percentiles on the threshold output, `variable`, and `NaN_count = total − Cardinality`. Deletes both transient proxies in `finally`. The numpy row builder (`_row_stats_from_values`) carries the same keys — the five percentiles and `M2`/`M3`/`M4` as the SUMS of the powered deviations, vtkDescriptiveStatistics' convention (`M2 = (n − 1) · Variance`), so a column is never half filled. **P10 / P90 are percentiles of the CELL values** (a tenth of the cells below P10), the convention of the calculator's chips, not the reserves convention; the column tooltips say so, and `Metrics ▾` has a `Percentiles` preset.
- `sum_meaningful(prop_kind, uom, kind_title, title)` — whether a Sum of the values means anything; each row of the matrix carries it, and a block none of whose rows has a meaningful Sum says `sum_meaningful: false` and draws no `Sum` column: a categorical property (codes), a unit in `node_kinds.PERCENT_UNITS` or a non-empty one in `FRACTION_UNITS`, a PWLS quantity class that `reconcile_dispatch._norm_class` reads as a fraction (of the kind title or of the property title), or a `health_dispatch.expected_domain` of `fraction`; unknown reads as meaningful, the column stays. The `stats_probe` op logs them with the five percentiles of each row and fails on percentiles out of order.
- Tree/state resolution: `_rep_path_for_array_path`, `_rep_title_for_array_path`, `_title_and_kind`, `_prop_kind_for_array_path`, `_unit_for_array_path` (the `uom` attribute FESPP writes on a property node, or the unit a derived property was given; `""` without one), `_resolve_vtk_name(tree, array_path, real_idx)` (MR → `<sanitized>_real_<idx>`), `_default_real_idx`, `_ts_label_for_idx`, `_PROP_TYPE_LABELS` (what a row's hover says of its values).
- Row builders: `_original_source_and_name(...)` (channel-aware: wellbore-frame channels read the per-channel extractor, not the frame source); `_row_stats_from_values(values, name, volume, pore_volume)`, the pure numpy row of an item or a part; `_build_view_row(...)`, the row `<property> On <view>` (one display as it is through `_compute_one_variable`, several or a cut scene through `drawn_cells.values` and `_row_stats_from_values`, each cell once; None when the view does not color the rep by this property or draws nothing of it; reads the view's realization and `pv_view.ViewTime`, `ts_label` the time in words).
- **Volume-weighted means.** An arithmetic mean gives one vote per cell, which on a grid whose reservoir layers are thin and whose overburden layers are thick is not the reservoir's porosity. Beside `Mean` each row carries `Mean (V)` — weighted by the cell volume — and `Mean (PV)` — weighted by the pore volume, volume × net-to-gross × porosity. The weights come from **`engine/cell_weights.py`** (`weights_for(state, tree, source_registry, rep_path)` → `{volume, pore, n, poro_title, ntg_title, poro_path, ntg_path, real_idx, note}`), which reads `volumetrics_dispatch.cell_geometry` and picks the two terms with `volumetrics_dispatch.auto_pick`, so the Statistics view and the Volumetrics card can never disagree about what a cell is worth — the harness asserts that identity: summed, the weights ARE that card's GRV and PV (drogon: 3 157 810 705.59 and 364 128 725.66, equal to 1e-9 relative). Cached per `rep_path`, 4 entries, FIFO; invalidation is EXPLICIT — `boot` calls `cell_weights.clear()` beside `load_generation += 1` and on `ui_loaded_rep_paths`. `weighted_mean(values, weights)` sums over the elements where the value is finite, the weight finite and `w > 0`, on the RAW index space **before** the finite-value compaction, so a value and its weight stay paired; `add_weighted_means` writes the two keys, `weighted_n` and `pore_n` — the pore weight is NaN wherever the porosity or the net-to-gross is blanked, so the two counts differ (drogon: 571 696 against 655 576). `weighted_mean` returns a third element telling "no element qualified" from "the two arrays do not index the same elements": a property read off the NODES of a grid arrives with more values than the grid has cells. A weight that qualifies on no element leaves its key ABSENT (the cell shows an en dash) — never zero. **`Mean (L)`**: on a blocked wellbore's row (`compare_rows._read_on_part`) the same `weighted_mean`, each cell weighted by how long the hole stays in it (`stats_supports.LENGTH_ARRAY`, written by the plugin). The keys are mirrored in the places that must move together — `compare_matrix._METRIC_KEYS`, `widgets/_shared/numfmt.js` `STAT_UNIT_POWER` and `widgets/compare/.../metrics.js` (`METRIC_KEYS`, `METRIC_LABELS`, `METRIC_TITLES`, `CSV_METRIC`, the `Central tendency` preset); `test_widget_fixes` parses those tables against `_METRIC_KEYS`. Ground truths: `tests/unit/test_stats_weights.py` (hand-derived: on volumes `[1, 9]` and values `[0.10, 0.30]` the arithmetic mean is 0.20 and the volume-weighted one 2.80 / 10 = 0.28; with `ntg = [1, 0.5]` the pore weights are `[0.10, 1.35]` and `Mean (PV)` = 0.415 / 1.45 = 0.286 206 896 5…, three distinct numbers) and `tests/unit/test_independent_derivations.py`, which re-derives the same figures by another method; harness: the `weights_probe` block of `scenario.py` (drogon Geogrid / Total Porosity: `weighted_n=655576`, `Mean=0.1614`, `Mean (V)=0.1626`, `Mean (PV)=0.2435`).
- **`_weights_note(tree, array_path, weights, rows)`** — what a row's weights could not be, said on the row's hover and in the CSV: a **view's row** (the filtered display, whose cells are not the grid's) and a **log channel** (no cell volume) are not weighted; a rep with no cells, cells unreadable, no porosity, net-to-gross taken as 1, a term that does not index the cells; when `weighted_n != Cardinality`, on how many of the valued cells the weighting was taken. And two disclosures the weight cannot avoid: on the porosity (or net-to-gross) term ITSELF the pore weight is the property, so `Mean (PV)` is that property weighted by itself and always reads above the plain mean — on drogon 0.2435, where the net-rock-weighted average the Volumetrics card implies (PV / NRV) is 0.2163 — and the weight is read ONCE per representation at `weights_for`'s `real_idx`, so a row pinned to another realization is weighed by that one's porosity and the line names both.

**State.** Reads `fespp_render_panels`, `visible_paths__<vid>`, `ui_active_realization_by_array_by_view`. Writes none.

**Collaborators.** `drawn_cells`, `view_axes`, `realization_dispatch`, `time_realization.label_for_time_value`, `make_valid_vtk_name`, `paraview.simple`, vtk numpy support. Consumed by `compare_dispatch`, `compare_rows`, `distribution_dispatch`, `crossplot_dispatch`, `stats_supports`.

**Gotchas.**
- **NaN strategy** — `Threshold(Between -inf..+inf)` is the canonical NaN drop so kurtosis/skewness stay meaningful; `NaN_count` is reconstructed as `total − Cardinality`.
- Wellbore channels are the special source case: the frame source lacks the channel array, so `_original_source_and_name` reads the channel's own persistent extractor.

### `fespp_on_trame/engine/property_values.py`

**Responsibility.** THE property-value seam: the one function every analysis consumer (stats, distribution, crossplot, derived recipes, synthetic logs) reads a property through. `values_for(state, tree, source_registry, array_path, rep_path, real_idx=None, ts_idx=None, component=_UNSET)` returns a 1-D float64 array, index-aligned with any other property of the same rep, NaN where a value is missing or blanked, or `None` (reason in `last_error()`).

**Key functions.**
- `values_for` — channel-aware (a wellbore-frame channel is ring-sampled off its tube, see `welllog_dispatch._ring_samples`), MR-aware (`real_idx` picks the `_real_<n>` array), TS-aware (moves the TimeKeeper for the read and restores it), derived-aware (`derived://` paths evaluate their recipe through the same seam). Folds the `vtkGhostType` cell mask (HIDDENCELL, 0.0-filled in the arrays) to NaN. **Vector-aware**: a property with several values per element (an `(n, c)` VTK array) comes back as ONE value per element.
- `reduce_components(raw, component)` — the vector rule: a scalar as it is; a vector reduced to `component` (an index) or, when `None`, to its magnitude. Flattening was the old behaviour and fed every statistic `c` interleaved values per cell, silently.
- `component_choice(state, array_path)` — the session's choice for that array from `ui_vector_component` (`{array_path: index}`; absent = magnitude). One choice per property, session-wide, so the colour (LUT `VectorMode` / `VectorComponent`), the statistics, the distribution, the crossplot and the synthetic logs all show the same thing — set through `controller.set_vector_component`, offered by the Colormap card's Component row when `cmap.components > 1`.
- `component_count(state, tree, array_path)` / `component_label(state, tree, array_path)` / `labelled(state, tree, array_path, label)` — how many values per element, the NAME of the component read, and a label carrying it after `COMPONENT_SEP` (a middle dot: VTK's text renderer draws brackets as parentheses on the 3D colour bar, so `[X]` read `(X)` there and `[X]` on every card). The count comes from the LIVE VTK array: the Colormap card counts the components it offers and `set_vector_component` publishes that count (`ui_vector_component_count`) beside the choice it writes, so a label and the select the reader picked the component in cannot disagree; the assembly's `componentCount` attribute is the fallback — a plain property leaf carries it, the collector's synthetic time-series and multi-realization leaves do not. The names are `""` on the magnitude, `X`/`Y`/`Z` on 3, `XX`/`YY`/`ZZ`/`XY`/`YZ`/`XZ` on 6, else `Component <n>` — the same naming as the Colormap card's select (`componentLabel` in `ColormapPanel.vue`: keep the two in agreement) — and the label reads `velocity · X`. The numbers change with the component, so what shows them says which one: `stats_dispatch` (card title, Original and View row labels), `crossplot_dispatch._axis_title`, `distribution_dispatch` (chart title, X axis, legend), `compare_dispatch` (chips, row labels, X title). The magnitude adds no suffix — it is the default.
- `_named_and_ghost(source, vtk_name)` — the array + its ghost array off the source's inner dataset (used directly by `distribution_dispatch`, which applies the same reduction).
- `display_label(state, tree, array_path, fallback="")` — THE name of a property wherever it is shown: the RESQML title (`propTitle` on a multi-realization / time-series node, the store's title on a derived one), the component read after a middle dot (`labelled`), the unit of measure in parentheses (`stats_dispatch._unit_for_array_path`: the `uom` attribute FESPP writes on a property node, or the unit a derived property was given) — `Total Porosity · X (m3/m3)`. No unit → no parentheses; the magnitude → no component; a path the tree does not know → `fallback` (the VTK array name at the colour-bar sites). Consumers: the 3D colour bar (`source_resolver.scalar_bar_title` for the leaf displays, `PdcScene` under BlockScope — the `BlockEntry.label` boot passes to `set_color`, re-issued through `relabel` when the component changes — and the IjkGrid shared instance's own bar), the Colormap card header (`ui_colormap__<vid>.label`) and its title-bar target, the Attributes card's "Colored by", `crossplot_dispatch._axis_title` (which appends its real / time suffix), the rows of the Statistics view (`compare_dispatch`). One rule, one text: a screenshot of the bar says what the numbers are, and the card the reader edits in agrees with it. Unit: `tests/unit/test_property_label.py`.

**Collaborators.** `stats_dispatch` (`_resolve_vtk_name`, `_original_source_and_name`), `assembly_index.inner`, `derived_props`, `welllog_dispatch`. FESPP tags a vector property node with a `componentCount` assembly attribute (the tree shows it as `×N`).

**Harness.** `vector_component_probe` op (scenario `vector_component`, `data/private/vector_props.epc`: `velocity` ×3, `stress` ×6) creates a recipe over the vector property, then reads BOTH at every component through `controller.set_vector_component`: the values must MOVE from one component to the next — compared by a digest of the values, since two components may share their bounds, hold the same values in another order, or differ only inside the envelope — and the title of the row in the Statistics view, the cross-plot axis title and the distribution title must carry `· X` / `· XY`… (`property_values.COMPONENT_SEP`) and nothing at all on the magnitude. It also asserts the live component count is published, without which a time-series or multi-realization property would be labelled `Component 0` where the Colormap card says `X`. `value_action_guard_probe` aims the four value actions at the representation a 3D pick resolves to: each must answer through the snackbar and open no panel. Unit: `tests/unit/test_vector_components.py` (the naming and the four label sites), `tests/unit/test_derived_vector_cache.py` (the cache key), `tests/unit/test_context_menu_targets.py` (what a right-click may offer, and the controllers' refusal).

### `fespp_on_trame/engine/crossplot_dispatch.py`

**Responsibility.** The cross-plot panel's charts: one X property against SEVERAL Y properties of the same rep (grid cells or frame rings pair by index; another rep is refused, never approximated), coloured by a third, as ONE plotly figure PER chart — the pinned snapshots first, then one live chart per Y row (`live:i`), each a plain x / y figure with no title of its own: the widget (`widgets/crossplot`, `CrossplotGrid.vue`) lays them out in rows of two squares under a caption line each, where the chart's Y is picked. The pieces, so the application can read the charts one by one: `crossplot_plan(state, tree, source_registry, x_path, ys, color_path, *, x_real, x_ts, log_x, log_y, pins, focus)` reads X and the colour ONCE and names every chart without reading a Y (`heads`, each `loading` when it has a Y); `crossplot_chart(plan, i, …)` reads chart *i*; `chart_public(chart)` is what the widget captions (`{key, title, pinned, kept, nan_y, nonpos_y, note, loading, group, group_title, step_title}` — `group` is the TRACK, i.e. the Y property whatever the date or realization it is read at, so the player can give one play button per property; `crossplot_chart` copies the three from the head it computes, or every chart would be a track of its own); `crossplot_figure(plan, chart)` → one `go.Figure` or `None` (no traces, or the plan focuses on another chart — the plan remembers which legend groups and colour bar the figures built so far have shown, so the legend is decided once over the grid); `crossplot_meta(plan, charts, drawn)` → `{kept, total, unit, nan, nonpos, nan_y, nonpos_y, note, rep_path, axes, drawn, focus, charts}` with `kept` = the candidate cells on screen at least once (the max over the drawn charts, never their sum), `axes` = `{key: ["x","y"]}` per drawn chart, `focus` = the key drawn alone or `None` when the asked one is not drawable (the grid is drawn instead; boot nulls `ui_crossplot_focus_<pid>`, and also when a Y row is removed — `live:i` keys are positional). `compute_crossplot_figures(…)` → `(figures, meta)` does all of it at once for the tests and the probes. **Progressive run (boot `_refresh_crossplot`, 2026-09-16).** The plan is built in the flush, the heads published with their loading marks, then an asyncio task reads the charts one by one (`await asyncio.sleep(0)` between two, a generation counter `_crossplot_gen[pid]` so a newer refresh stops the older run) and ships the growing figure list after the 1st, 2nd, 4th, 8th… chart and at the end — a state var travels whole at every flush, so shipping after every chart would cross the socket n²/2 times a figure; doubling keeps the total under twice the final list. Every figure carries `rev = "<gen>:<key>"`: the widget hands plotly the same object for an unchanged `rev` (no redraw of the charts already there) and keeps the previous figure on screen under the busy bar while its chart is read again (R9), so a log toggle updates in place and the zoom survives. **WebGL budget.** A browser holds about sixteen WebGL contexts, and every chart past that came up blank (no axes, no grid): past `GL_CHARTS = 8` charts the traces are SVG `scatter` (not `scattergl`) over a smaller cloud (`MAX_POINTS_SVG = 3000` → `_x_context(max_points=…)`), for every chart, so the candidate cells stay the same for all — unless the plan is built `film=True` (the widget's Player layout shows one chart per track: a handful of contexts on the page, every chart keeps the full WebGL cloud). `MAX_CHARTS = 100`: the Y rows past the budget (pinned snapshots count) are not drawn and the note says `N charts asked: the first 100 are drawn`. **Player (2026-09-17).** `layout` (`grid` | `player`) is a settable key (a switch recomputes, the figures on screen staying under the busy bars, and it clears both zooms — the grid's `focus` and the player's `track`); the transport writes nothing but display state and never recomputes (`_crossplot_play_set`): `step` (`[track, index]`, clamped to that track's charts — every track when `sync` is on), `speed` (charts per second, 0.05–20), `sync`, `track` (the track shown alone; an unknown one is refused), and the action `play` (`[track, on]`, every playable track when `sync` is on or the track is `None`). ONE asyncio loop per panel (`_crossplot_play`, like the Time card's) advances every track marked in `ui_crossplot_playing_<pid>` modulo its own chart count and ends by itself when nothing is left to play, the panel closes, or a track falls under two charts. `_crossplot_tracks` reads the published charts' `group`; `_crossplot_prune` (every refresh) drops the steps, the marks and the zoom of tracks that are gone and clamps the rest. In player mode the plan is built with `focus=None`: the player draws EVERY chart (it steps through them), and shows one per track. `_compact` rounds every trace number to seven significant digits relative to the largest (a chart is read at a few hundred pixels; the selection is recomputed server-side at full precision) — half the bytes of a figure. **Category names (2026-09-11).** When the colouring property is a `CategoricalProperty` whose codes have names (`categories.labels_for` through the LUT annotations or the fesapi StringTableLookup), each trace is named by the label (`categories.label_of`) and grouped by the code (`legendgroup = f"{cat:g}"`, a stable key); a `DiscreteProperty` has no names and its legend reads the codes. The lasso count in the note is written by `numfmt.fmt_int`.

**Key functions.**
- `_x_context` — X read once; ONE uniform stride `ceil(n / MAX_POINTS)` (`MAX_POINTS = 20000`) on the original index, colour categories fixed over the whole candidate set; each chart then applies its own finite mask (`> 0` on a log axis), so every chart shows the same candidate cells and a NaN in one Y never empties another. `customdata` = original cell ids. Its notes ACCUMULATE (`_note`: `"uniform subsample: 1 point in 47 · colour ignored: …"`), one never replacing another. The meta counts what is NOT drawn apart, over the whole arrays: `nan` / `nonpos` (X without a value / X ≤ 0 on a log axis), `nan_y` / `nonpos_y` (the pairs X has that Y cannot complete — those of the chart that gives `kept`, and per chart in `charts[]`), and `unit` = `sample_unit(tree, rep)`: `cells` on a grid / sub-rep / blocked wellbore, `samples` on a Frame (a log has 216 samples, not 216 cells: `values_for` reads one value per frame node, never the tube points), else `values`. The widget's badge reads them first — `13,948 of 926,808 pairs · 271,232 cells without a value (271,232 on X) · 12 ≤ 0 on a log axis` — and appends the notes, so a subsampled cloud is never mistaken for the whole grid; a chip's tooltip carries its own chart's Y-side counts. `selection_cell_ids` says `N cells / samples selected` with the same unit.
- **Zoom survives a refresh** (`layout.uirevision`, per axis too): plotly keeps the reader's pan / zoom across `Plotly.react` as long as the axis's `uirevision` is unchanged, and trame-plotly's client does react on a data change (not a new plot). The keys name what is ON the axis, not the data: `layout.uirevision` and every live `xaxis.uirevision` = `<rep>|<axis_key(x)>|lin/log`, each live `yaxis.uirevision` = `<axis_key(y)>|lin/log`, a pinned chart's = its key and titles — where `property_values.axis_key(state, path)` = `<path>#<component read>` (`mag` on the magnitude): another time step or realization redraws inside the same framing, another property, another COMPONENT (`set_vector_component` recomputes every plot: a zoom made on X kept for an axis now labelled Z would lie) or a log toggle re-frames that axis alone. The same rule holds for `distribution_dispatch` (`<axis_key>|log_y|norm|cumulative`), `compare_dispatch.dist_figure` (`<x title>|log_y|norm|cumulative|<axis_key of every item>`) and the calculator preview (`<rep>|<formula>`). Unit: `test_uirevision_follows_the_axes_not_the_data`, `test_uirevision_holds_across_a_binning_change`; browser: `tests/browser/specs/08-charts.spec.mjs` (a drag zoom, a log Y refresh keeps the x range, a log X re-frames it; the Statistics view's distributions across a bin count).
- `snapshot_chart` — a pinned chart: frozen plain trace dicts `{traces, x_title, y_title, label, kept, log_x, log_y}` kept SERVER-SIDE (boot `_crossplot_pins[pid]`, never in state) and re-added verbatim (`go.Scattergl(dict)`) on every rebuild; survives any later change of the axes. `label` tags the whole chart with a realization / time only when both axes agree (or one has none) — real 3 vs real 4 is said by the axis titles and the label stays empty.
- `chart_key_for_selection(meta_axes, sel)` + `selection_cell_ids(...)` — the box / lasso geometry arrives with the key of the chart it was drawn on (`{chart, range, lasso}`; the chart is read from `sel["chart"]` first, `meta.axes` is the fallback), then the FULL-resolution mask is recomputed with THAT chart's Y (real / ts) and X shared; boot `crossplot_select` lights the ids in every 3D view (`_select_ids(blocks, "CELLS", ids)`) and writes the count into `meta.selected` — on a subsampled cloud the note adds `at full resolution (the chart draws 1 point in N; the region is read over every value)`, the same stride rule as `_x_context`, so a count larger than the drawn dots reads as intended (2026-09-15); `None` (deselect) clears. A selection on a pinned chart is refused (`meta.selected = "pinned chart: selection off"` — its cells belong to a past state of the axes); a selection on a frame channel lights nothing and says so in the badge (`meta.selected = "selection on a well log is not linked to the 3D view"`).

**State (per panel `<pid>`).** `ui_crossplot_x/xreal/xts/xopts`, `ys` (`[{path, real, ts}]`), `yopts` (aligned), `color`, `logx`, `logy`, `choices`, `figures` (`[{key, rev, data, layout}]`, one per drawn chart), `meta`, `charts`, `focus`, `layout` (`grid` | `player`), `step` (`{track: index}`), `playing` (`{track: True}`), `speed`, `sync`, `track`. ### `fespp_on_trame/engine/compare_tree.py`

**Responsibility.** The docked tree of the Statistics view: kind -> representation -> property, then the parts of the grids. What a path is comes from `compare_dispatch` (its facts, the load states `LOADED` ... `FAILED`), which knows nothing of this module. Also `extract_folder(tree, part)`, `tree_tabs(xml)`, `settle_pending(pending, loaded, finished)`, `PARTS_KIND`, `PARTS_FOLDER`. Pure: no trame, no ParaView at import. A tick on a folder of parts asks like a folder of properties: a panel's read counts the parts of a grid (`app/features/tick_question`), and the box then says `objects` (`tick_confirm.question(objects=True)`).

- `assembly_property_paths(tree)` → every property the FILE holds, loaded or not — one walk of the assembly through the shared `Tree.iter_nodes` (a node and its DIRECT children, the walk `health_dispatch.tree_findings` takes too), keeping the nodes whose element type tracks as an ARRAY (`element_type.for_kind(type).tracking_bucket() == BUCKET_ARRAY`) and dropping the `!!!PARTIAL!!!` stubs (`node_kinds.PARTIAL_PREFIX`, now the one spelling of that marker outside `tree.py`). The bucket, not `node_kinds.PROPERTY_KINDS`: that constant also holds the generic kind `"Property"`, which no element type claims, so it never reaches `ui_loaded_array_paths` — a leaf offered for it would load and then be declared "not loaded" for ever. A `MultiRealization` / `MultiRealizationTimeSeries` node is yielded and its SUBTREE skipped, mirroring the widget's `COLLAPSE_RE`: its per-realization children carry the same title and would be listed as so many identical leaves. The kind, the rep and the title are attributes the reader wrote on the node, so listing costs no read: the docked tree is full the moment the view opens, and `boot._compare_listed_paths` = this walk + the derived recipes (which live in the store, not in the assembly). **This also fixed the health counts**: `tree_findings` used `vtkDataAssembly.GetChildNodes(nid)`, which walks the whole SUBTREE by default and handed every node back once per ancestor — drogon read "1 435 objects · 164 partial" where the file holds 405 and 41.
- `load_state(path, loaded, pending)` → `LOADED ("")` | `UNLOADED` | `LOADING` | `FAILED`, and `_LOAD_INFO` the sentence each one puts on the leaf.
- `tick_plan(ticked, items, loaded, pending, max_load=None)` → `{items, to_load, pending, confirm}` — what a tick in the docked tree means: an item per ticked property, every item of an unticked one dropped, and a property the session has not read in `to_load`, which boot writes into `state.selected_paths` (the very channel the data tree writes, so every cascade of the load pipeline applies) while it waits in `pending`. An untick NEVER unloads — a 3D view may be showing that property. A derived recipe is never in `to_load` (no node to select). **`max_load` is the size above which one tick ASKS FIRST** (`tick_confirm.MAX_TICK_LOAD` = **20**, passed by `boot.compare_tree_paths`; **2026-09-13**: it used to be a flat refusal, which the product owner read — rightly — as a cascade that "selects nothing"; the threshold then left `compare_dispatch` for `engine/tick_confirm.py`, which every tree of the application shares). A folder standing for more unread properties than that comes back whole in `confirm` with the plan left EXACTLY as it was: no item joins, nothing is read, nothing waits. `boot._compare_ask` keeps `{vid, ticked}` server-side and raises the application's ONE question through `boot._ask_tick` (`state.ui_tick_confirm = tick_confirm.question(n)`, the box drawn once in the layout); `controller.tick_confirm_answer(bool)` either replays THE SAME tick uncapped (`_compare_apply_tick`, so what the question announced is what the yes does) or drops it and lets `_sync_compare_tree_selection` put the boxes back. That sync stands back while a question is open (`_compare["confirm"]`), or the tick would be written away under the dialog; the question also dies with its panel and with a new `assembly_xml`. Boot asks for the read through `_compare_request_load`, which hands `_apply_selection(..., ask=False, push=True, shown=False)` only the paths that are NOT in `selected_paths` already — `shown=False` is the panel rule (**2026-09-14**): the properties and the representations the cascade pulls in are born hidden (`boot._panel_reads`), read into the view and shown in no 3D view. A path already selected starts no load cycle and would wait for ever — it is set `FAILED` at once and named on screen instead. `settle_pending(pending, loaded, finished)` → `(pending, failed)`: what arrived stops waiting, and once the load cycle is OVER what did not arrive turns `FAILED` rather than spinning for ever.

Reps are grouped by rep PATH and titled by `stats_dispatch._rep_title_for_array_path` (the grid's name, not the "SolidColor" geometry leaf). ### `fespp_on_trame/engine/compare_rows.py`

**Responsibility.** The rows of the matrix beside the selection itself. At each refresh the items of a tab are expanded (`with_following(state, tree, items, parts)`) into the rows of the matrix: an item, then right under it its FOLLOWING rows, `{path, real, ts, uid: "<item uid>@<support>", pinned: False, xplot: False, support, follows: <item uid>}`. The uid derives from its item's, so it is stable across refreshes.

- **A part's row** (`support` = the part's path): one per open part of the item's grid (`ui_compare_parts`; `stats_supports.belongs_to`), under each unpinned item, at that item's realization and time step. `_read_on_part`: the property on the part (`stats_supports.part_values`), with the grid's weights taken on its cells; on a blocked wellbore the mean along the hole, `Mean (L)`, from the plugin's cell array `Interval length` (`stats_supports.LENGTH_ARRAY`), and none of the grid's weights.
- **A 3D view's row** (`support` = `view:<vid>`, `is_view_row`, `view_of`): automatic, no gesture. One per (property, view) that shows the property (`visible_paths__<vid>`) and cuts or filters its grid (`_cutting_views`: `stats_dispatch._resolve_rendered_inputs` not empty — a threshold, a slicer, a cell mask, a cut of the whole scene; a view showing the whole grid has none, its row would be the item's again), under the first unpinned item of the property, at the view's realization and time. Label `<property> On <view title>`. Read by `stats_dispatch._build_view_row`, inside one `transient_chain`, its proxies unseen.

A following row is sorted, read against the baseline, drawn in the overlaid distribution and written in the CSV like any other; it has no picker and no pin, is never the baseline and never on a cross-plot axis, and neither the tab nor the block count it. A filter or an extract can change it with no signature to tell, so it is never kept in the row cache (`compare_dispatch.READS`).

**What moves a 3D view's row.** No state says what a view draws, so a lifecycle event does: **`view_cuts(vid)`**, emitted by `_push_threshold_state`, `_push_slicer_state`, `CardHost._redraw` (a live drag or a player step settles nothing) and the occupancy's `on_settled`; `session_rows` covers the eye pass, `ui_per_view_time_pulse` the view's time. `app/features/compare_parts` re-arms a 0.4 s batcher timer per burst (`compare:cuts`), then compares **`cuts_read(state, tree, items, isolates, scenes)`** — per property and view that cuts its grid: the scene's boxes, the cuts, the threshold chain, the masks and the view's time — with its last value: when it moved, `_refresh_compare_rows` reads the matrix and the overlaid distributions again (chips and cross-plot read the items and stay). So a node click or a z-scale does nothing. `controller.heavy_pending` does not see that timer: a probe polls `ui_compare_rows`.

- `support_row(state, tree, source_registry, it)` → `(stats | None, note, facts)` for `compare_dispatch._row`; `support_values(...)` → the values the charts draw (`last_error()` says why None); `naming`, `where_read`; `row_facts(state, tree, path, real, ts)` → what every row says of itself beside its figures (`value_type`, `sum_meaningful`, `real_read`, `ts_text`).

### `fespp_on_trame/engine/welllog_dispatch.py`

**Responsibility.** The well-log correlation panel's payload: `build_payload(tree, source_registry, well_paths, selected_paths, flatten_on=None, strati_columns=None, synthetics=None)` → `{wells, markers, flattenOn}`, the shape `widgets/welllog` draws. Reads the CHECKED channels and markers of every wellbore sent to the panel and computes the zone statistics. **The stratigraphic band is what the marker frame STATES (PO decision, 2026-10-05; built 2026-10-10, FESPP rebuild needed):** the column used to be laid onto each well (`strati`) from its CHECKED markers matched by title, so unchecking a marker changed the stratigraphy — a guess shown as a fact. Now `_frame_strati` asks the plugin's query channel for the typed fields of every marker frame under the wellbore (`repo_query.object_fields`: `md` of every marker, `marker.<i>`, `unit.<index>` the occurrence interpretation lists (titled by the unit interpretation, or by its feature when that is unnamed — SKUA writes `|UNNAMED|` — as the stratigraphy view names its ranks), `interval_units` the unit index per interval — RESQML 2.0.1 `IntervalStratigraphicUnits`, read over every marker of the frame whatever is checked) and `frame_bands` (pure, unit-tested) turns them into bands in MD — consecutive intervals of one unit merged, "null" intervals left open, the colour borrowed from a loaded column's entity of the same title, grey otherwise; on a well drawn in TVD the bands are placed through the markers' own (md, tvd) pairs (`_md_to_tvd`), and not at all with fewer than two. A frame without the assignment gives no band: nothing is read off the marker titles. `zone_intervals` then says `source: "frame"` (the widget: "zones from the marker frame's own stratigraphy"). `stratigraphy.intervals_for_tops` and `_strati_intervals` stay, unused by the payload.

**Key functions.**
- `log_channels(tree)` — every log channel of the tree by well, `[(well title, channel uuid, channel title, uom)]`, from the tree's attributes alone (the plugin's `uom`): what the time-depth model's pre-fill picks its time logs out of (`engine/time_depth_prefill`, 31/10).
- `_fetch_block(shared, selector)` — one PDC block through a transient `ExtractBlock` (`Assembly = "Assembly"`, or a `/data` selector matches nothing). `_ring_samples(ds, name)` — one sample per frame node off the tube (the tube repeats each node `nSides` times); FESPP writes a gap as NEGATIVE ZERO because a NaN radius destroys the tube and counts them in `<array>_nanCount`; a negative zero is a gap only on a block that counted some (`ranges.no_value`, `ranges.gap_count`: the rule the statistics and the log view read gaps by), the count checked against what survived; a vector channel reads as its magnitude. Each sample carries TVD (−Z) and MD (a field array, when the plugin ships it); the axis is chosen per well.
- `zone_intervals(well)` → the rock lane of the column laid onto the well, else the intervals between consecutive markers (`source` = `"column"` | `"markers"`; since 2026-10-05 always `"markers"` from `build_payload`). A marker zone is named after BOTH its picks (`TopA → TopB`): named after its top alone it read as a formation, and silently grew past it when the next marker was unchecked. `zone_stats(well, cutoffs=None)` → per zone, per curve: `n, mean, min, max, p10, p50, p90` (nearest-rank percentiles, `_percentile`), bottom bound exclusive; with cutoffs also `net, ntg, phih, hcph` and per curve `n_pay, mean_pay` — or, when a rule names a log the well does not carry (`missing_rule_curves`, a multi-well panel offers every well's logs to the editor), every one of those `None` and the missing names in `pay_na`: not evaluable is not zero, and the panel shows a dash with the reason.
- `pay_intervals(well, cutoffs)` — pay is where EVERY rule (`{curve, op, value}`) holds, evaluated sample-and-hold on the union of the rule curves' depths (`_step_hold`): a gap or a depth above a log's first sample is not pay. `with_cutoffs(payload, cutoffs)` — a NEW payload per panel (each panel has its own rules, `welllog_cutoffs__<vid>`) on the shared base. `_pore_thickness` — Φ·h and Φ(1−Sw)·h when a porosity and a water-saturation curve can be told from their property KIND (`_curves_of_kind`: every curve whose kind names "porosity" / "water" + "saturation", the FIRST in track order being read), `%` scaled to fractions. `summation_curves(well)` → `{phi, phi_candidates, phi_absent, sw, sw_candidates, sw_absent}`, carried on each well by `with_cutoffs` as `summation` (with `pay_na` and `pay_na_why`): the report NAMES the logs it read, the others that matched — a neutron porosity says "porosity" too, so the pick must be visible (matching the exact PWLS kind instead of the word is a candidate improvement of the rule; the rule itself is unchanged, only disclosed) — and, in `phi_absent` / `sw_absent`, the absent channels of the kind with why, so the panel names the porosity it would have read instead of "no porosity".
- `absent` — per well, from `build_payload`: `{channel title: {kind, why}}` over the channels the wellbore logs that yielded no curve — `"unticked"` (channels are ticked per wellbore, so in a multi-well panel a log ticked on one well is unticked on the next) or `"unreadable"` (ticked, no sample came back: block not materialised, array missing, nothing but gaps). `absent_why(well, name)` → that code, or `"unlogged"` when the well names the curve nowhere; `with_cutoffs` puts it on each well as `pay_na_why = {curve: why}` and the panel words each — "not ticked for this well (tick it in the well tree)", "ticked but no sample could be read", "not logged on this well" — where one wording for all three was false in the common case.
- `synthetics` — `{well_path: [curve]}` from `trajectory_sampling.curves_for`, admitted like channels so each lands in the track of its kind, flagged `synthetic` (drawn dashed). **One value scale per track** (**2026-09-15**): each track carries `range` = the span of every curve of the kind across the wells, and the widget draws every curve on it (`correlation.js trackScale`; the header says the track's two ends under the kind, and each curve's own span beside its name). Before, each curve had its own scale and a flat synthetic was a line across the whole track — the disagreement with the measured log, the point of the synthetic, could not be read.
- `_full` — every curve's undecimated samples per well (`{name: [[value, draw, tvd]]}`): `_decimate` (MAX_SAMPLES) only shrinks what is DRAWN; `zone_stats`, `pay_intervals` and `_pore_thickness` read `_full` when present so a zone's `n`, its pay and its net are not one sample in k. `boot._refresh_welllog` strips it before the payload crosses the websocket.
- **Two axes (2026-09-12, lot 3).** The DRAWING axis (`depthRef`, unchanged: measured depth when every sample and every pick of the well carries one, TVD otherwise) is what `samples`, `depth`, `tops[].depth` and the stratigraphic bands are expressed in. The INTEGRATION axis (`integrationRef`, always `"TVD"`) is what every thickness is summed on: `_step_hold`, `pay_intervals`, `_pore_thickness` and `zone_stats`'s sample selection all read `_tvd_pairs` (slot 2 of a triplet; a pair-shaped fixture sample means "the one depth IS the vertical"). A thickness along the hole overstates the rock by 1/cos(inclination) — 39 % on Volve's reservoir zones — and the split also makes the table invariant when a synthetic log (no MD) flips the drawing axis. Each zone carries FOUR bounds (`top`/`bottom` drawn, `top_tvd`/`bottom_tvd` vertical), `thickness_tvd`, and `tvd_na` — the verbatim reason a horizontal or re-entrant zone reports no thickness (it keeps its curves, selected on the drawn axis, and every summation is `None`). Each top carries `tvd`; the column's bands are mapped back through `_tvd_of_draw` (exact on a pick, linear between samples, else `None`). `up_hole_tvd` / `well["tvd_up_hole"]` counts the metres of hole that come back up, disclosed in the panel's note. The PAY follows the same split: `with_cutoffs` publishes `pay` on the DRAWING axis — the renderer scales the green band with `depth.min`/`depth.max`, so vertical intervals shaded there land hundreds of metres too shallow on an MD well and clip away entirely on a steeply deviated one — and `pay_tvd`, the same pay on the vertical, which is what `zone_stats` and `_pore_thickness` sum over. `_pay_spans` walks the flag once and returns both bounds of every stretch, each read off the sample that bounds it rather than interpolated back. The `welllog_probe` asserts every published `pay` bound lies inside the well's drawn track (Volve: 406 bands, 0 outside). **Prerequisite fixed the same day:** `_ring_samples` took the FIRST point of each tube ring as the depth — a point on the tube SURFACE, at a radius the log value drives: up to 69.37 m off the trajectory on Volve, going back up on 2 912 steps and breaking |ΔTVD| ≤ ΔMD by 5.02 m. It now takes the ring's MEAN Z, which is its centre, hence the trajectory point (it agrees with the markers' own depth to 0.000 m). The `welllog_probe` asserts `tvd_monotonic=0/N`, `max(|dTVD|−dMD)=0` and `0 ≤ gross_tvd/gross_md ≤ 1.05` on every zone. **Ground truth.** The figures are not read off the code: `tests/unit/test_zone_stats.py` runs a synthetic well inclined at a constant 60° (`cos 60° = 0.5`, so TVD = MD / 2 exactly), whose net, N/G, Φ·h and Φ(1−Sw)·h are derived by hand in the test's docstrings (zone A of TVD [500, 550): pay [500, 520] ∪ [540, 570], net 20 + 10 = 30 m, N/G 0.60, Φ·h 3 × 0.20 × 10 = 6.00 m, Φ(1−Sw)·h 4.20 m — half of what the along-hole integration used to report), and `tests/unit/test_independent_derivations.py` re-derives the same numbers a second time by another method (a midpoint Riemann sum instead of the segment sum). The per-curve statistics are asserted UNCHANGED: a zone bounded in TVD selects exactly the samples its MD bound selected.

**State.** Read by `boot._refresh_welllog` (runs only when a well-log panel exists): `ui_welllog_wells`, `selected_paths`, `ui_strati_columns`, `ui_welllog_synth`, per panel `welllog_cutoffs__<vid>` and `welllog_flatten__<vid>`; writes `welllog_data__<vid>`.

**Zones export (2026-09-11).** `zones_csv_payload(payload, cutoffs)` → `welllog_data__<vid>.csv` (`{name, header}`, `EMPTY_PAYLOAD` when no well has a zone): name `zones_<well slug>` (one well) or `zones_<n>_wells`; header = the wells, the zones source (column / markers), the cutoffs (`curve op value` or `none`), the porosity and water-saturation logs read per well and — since lot 3 — TWO axis fields instead of one: `depths` (top and base in each well's own drawing axis, named by the `depth_axis` column; `top_tvd` and `base_tvd` true vertical, all in the frame's own unit, not declared in the file) and `thicknesses` (`gross_tvd`, `net_tvd`, `phih_tvd` and `hcph_tvd` integrated on TRUE VERTICAL DEPTH, `gross (depth_axis)` being the along-hole interval the band is drawn over and not a thickness of rock, `ntg = net_tvd / gross_tvd` a fraction, a curve's statistics in its unit). The widget's `Copy CSV` button (`.wlc-zones-head`, disabled without a row) writes the rows raw from `zoneRows`: `well,depth_axis,zone,zone_source,top (depth_axis),base (depth_axis),top_tvd,base_tvd,gross (depth_axis),gross_tvd,net_tvd,ntg (fraction),phih_tvd,hcph_tvd,curve,unit,n,mean,mean_pay,p10,p50,p90,min,max,note` — a gross row's curve columns empty, a summation that could not be evaluated `n/a` with its `pay_na` reasons joined in `note` — and, since lot 3, `gross_tvd` itself is `n/a` on a zone whose two bounds have no usable vertical depth, with that zone's `tvd_na` sentence in the same column. The zone table's numbers and percentages are written by the shared rule (`fmt`, `fmtPct`, `fmtInt`; `welllog/src/correlation.js` imports it too, so `demo.html` loads it as a module over http). Browser: `13-zones-export` (a sandbox well); a hand check on a Volve well through `_local/browser-check.ps1` remains worth doing for the wording.

### `fespp_on_trame/engine/trajectory_sampling.py`

**Responsibility.** A grid property sampled along a wellbore trajectory — the synthetic log. `synthetic_curve(state, tree, source_registry, well_path, array_path, step)` → `{name, unit, kind, samples: [[value, tvd, md]]}`; `curves_for(...)` serves the panel's `[{well, prop, step}]` requests (`ui_welllog_synth`, session-wide).

**How.** `stations_and_md` (and `trajectory_stations`, its first half) reads the trajectory block in POLYLINE order (`_polyline_order`): the stations' md is the file's measured depth when the block carries the `MD` point array FESPP writes since 2026-09-15 (`ResqmlWellboreTrajectoryToVtkPolyData`, from fesapi `hasMdValues` / `getMdValues`, one value per station, absent on a trajectory without stored MD) and pairs with the points (`_true_md`: same count, no NaN), else `chord_md` makes it the cumulative chord length from the first station; `resample` walks it at a fixed step. `sample_grid(dataset, values, points, with_md)` writes the md slot only when the md is the file's — a chord length is not a measured depth, and `welllog_dispatch` draws a well on TVD as soon as one sample lacks md. `sample_grid` builds a `vtkStaticCellLocator` on the rep's inner dataset — the SAME dataset `values_for` reads — so `FindCell` ids index the property's values directly (ghost cells are already NaN). The property must be loaded (its rep in the source registry); the choices the editor offers are `welllog_synth_choices` (`boot._on_welllog_synth_choices`: the panel's wells, the loaded properties living on an IjkGrid / UnstructuredGrid).

### `fespp_on_trame/engine/reconcile_dispatch.py`

**Responsibility.** Well ↔ model reconciliation by property KIND — the `reconcile` view kind (`app/views/reconcile_panel.py`, widget `widgets/reconcile`, controllers `open_reconcile` / `reconcile_compute` / `reconcile_auto_pairs` / `reconcile_set_pairs` in boot, payload in `ui_reconcile`). For every well of the log view (`ui_welllog_wells`) and every CHECKED log channel, the loaded grid properties of the same `propertyKind` are sampled along the trajectory through `trajectory_sampling.curves_for` and admitted to a `welllog_dispatch.build_payload` as synthetics — which puts the well on TVD and lays the zones (`zone_intervals`: column, else marker pairs, else the whole well) on the same axis as both curves. `rows_for_well` (pure, unit-tested) then aggregates log and grid samples per zone: n, mean, P50, Δ, Δ/|mean|, z = Δ/σ_log; `sort_rows` puts the largest |z| first. **Few samples (2026-09-11, PO decision).** A zone with fewer than `MIN_SAMPLES = 5` log samples has a z that means little (three near-constant samples give a tiny σ and a huge z): the row carries the flag `n<5` (a chip in the widget, tooltip "too few for the sort — the row is ranked after the others"), `sort_rows` ranks every such row after the others whatever its z, and the payload carries `min_samples` for the widget's summary (`N rows · M beyond 2 σ · K with n<5` — a flagged row is counted in K only, never in M: its z means little). Never dropped, never silent.

**Pairing** (`match_basis` / `auto_pairs`): exact kind title → `kind`; one kind a specialisation of the other in the PWLS 4.0 hierarchy (`engine/pwls_kinds.py`: "water saturation" under "saturation", "neutron porosity" under "porosity") → `kind~`, the row flagged "`a ⊂ b`"; two PWLS kinds that are merely siblings or cousins (water / gas saturation) NEVER pair; kinds the hierarchy does not know (RESQML 2.0.1 enum names such as "gamma ray API unit", Petrel's local kinds) fall back to a shared word of ≥ 4 letters → `kind~`; no kind on a side → titles, `name` / `name~`. **Short mnemonics** (`_MNEMONICS`, `_tokens`): a word under four letters pairs nothing, except a curve mnemonic written as a WHOLE word — `SW`, `SO`, `SG`, `PHI`, `NTG`, `GR`, `VSH`, `RHO` — which also yields from the words naming the same quantity (`WatSat`, `SWAT` → `sw`; `poro`, `porosity`, `PHIE` → `phi`; `GammaRay` → `gr`…), so `SW ↔ WatSat` is a `name~` pair while `SW ↔ Swept zone` (a prefix) and `Zone A1 ↔ Layer A1` (a two-letter word that is no mnemonic) are not; unit: `test_short_mnemonics_pair_as_whole_words_only`; two declared kinds that disagree never pair. A log keeps only its best basis. The hierarchy ships as `fespp_on_trame/assets/pwls40_kinds.json` (`{title: [parent, quantity_class]}`, 3 919 kinds, one root "property" — which names ITSELF as parent in the EPC), derived by `scripts/gen_pwls_kinds.py` from Energistics' `eml23_pwls40.epc` (11 MB, kept out of the repo under `data/private`). The user's own list (`reconcile_set_pairs`, basis `manual`) replaces the automatic one until `reconcile_auto_pairs`. **Units** (`unit_factor`): percentage units (`%`, `p.u.` — **2026-09-15**, `node_kinds.PERCENT_UNITS`, the one vocabulary the volumetrics and the well-log cutoffs read through `node_kinds.percent_factor`) ↔ fraction units (`""`, v/v, m3/m3, euc…, `node_kinds.FRACTION_UNITS`) are scaled on the LOG side and flagged; anything else different is flagged and left alone. A porosity log in p.u. against a grid in v/v used to read as a ×100 disagreement.

**Quantity class, and the length weight (2026-09-12, lot 3).** `rows_for_well` now bounds every zone on the TRUE VERTICAL depth (`welllog_dispatch._tvd_pairs`, the axis the log view sums on), so a zone holds the same samples in both tables; a zone with no usable vertical bound falls back to the drawn axis and says so in its flags. Each row carries `class_log` / `class_grid` (`quantity_class_of`: the side's KIND's PWLS quantity class, or, failing that, its TITLE's), `class_checked` and `class_mismatch`. `_norm_class` reads the uninformative classes (`""`, `"unitless"` — 1 368 kinds inherit the root's) as unknown and folds every spelling of a ratio of like quantities (`volume per volume`, `dimensionless`, `length per length`…) into one `fraction`, so a porosity and a saturation still pair; enumerating the 3 919 shipped kinds shows **0** whose normalised class conflicts with an ancestor's, which is why the guard cannot break a `kind` or `kind~` pair (unit: `test_the_shipped_hierarchy_has_no_conflicting_ancestor_class`). A mismatching pair is DEMOTED, never dropped: `+10` on its basis rank in `auto_pairs` (any unmismatched pair of that log wins), the verbatim flag `different quantity classes: a vs b`, and a new first key in `sort_rows` that puts it below even the `n<5` rows; an unknown class reads `quantity class not checked`. Note that `match_basis` already refused two KNOWN unrelated kinds, so the guard only ever fires on the shared-word branches. Beside `mean_grid`, each row also carries `mean_grid_len` and `len_grid` (`traversed_lengths`): the grid mean weighted by the length of hole actually traversed inside the zone — each sample owns the half-step to each neighbour, clipped to the zone and floored at 0 — the widget's `Mean grid (L)` column. EVERY sample that owns a positive length is weighed, including a station that falls just outside the zone but whose stretch reaches in, so `len_grid` is the zone's own traversed span and not one sampling step short of it (zone [0, 11) over stations 1…11: 110/11 = 10.0 over 11 m, not 1.0 over 10 m). The `lo <= d < hi` gate stays on the unweighted `mean_grid`, which still drives `gap`, `rel`, `z` and the ranking. `with_classes` re-attaches `class_log`, `class_prop`, `class_mismatch` and `why` to every pair `compute` publishes — a hand-edited list comes back as `{log, prop, basis}` alone — and the widget renders `why` as the pair chip's tooltip and marks a demoted pair amber, so a pairing nobody should read is visible in the strip even when its zones hold no sample and it yields no table row. **Harness.** The `reconcile_probe` block prints per row `class_log` / `class_grid` / `class_checked` / `class_mismatch` and `mean_grid_len` beside `len_grid`, raises on any `class_mismatch` and on a row count other than the scenario's `expect_rows` (`welllog_reconcile.json`: `2` — on Volve `SW ↔ WatSat`, both `dimensionless`, checked and clean, and `Facies_Wilfried ↔ Lithology1`, two PWLS-unknown kinds, not checked: the guard must neither drop nor add a row on this data). The same block also runs the WHOLE promise of L3-1 on real data: it rebuilds the log payload WITH the grid curves sampled along the trajectory (`trajectory_sampling.curves_for`), applies the same P50 cutoff to both payloads and raises when any zone's `thickness_tvd`, `net`, `ntg`, `phih` or `hcph` moves — a synthetic log flips `depthRef` to `TVD` and must move nothing else.

### `fespp_on_trame/engine/tree_grammar.py` — what a tick and an eye mean (2026-09-13)

**Responsibility.** The pure half of the one grammar every tree of the application follows (rewritten with the PO on 2026-10-18). A **checkbox** is the session's load, common to every view: ticked in any tree = read and kept, and in the tree of a PANEL what it read also goes in that panel; unticked = unloaded from the session, after a confirmation naming the views that use the object when another one does. An **eye** is "shown in THIS view": drawn in a 3D view, held by a panel (a row of the Statistics view, a well or a curve, a table row); it is offered on what the session holds and never reads.

**Routing (2026-10-18).** Every tree's checkbox sends one event, `tree_tick` = {vid, kind, paths, t} (the Statistics view: `compare_tick`, in its synthetic paths, mirrored from the selection into `compare_tree_loaded__<vid>`), handled by `_tree_tick` in `app/features/tick_question`: `_apply_selection(paths, origin=vid)` asks before unloading what `panel_trees.users(...)` finds elsewhere (`tick_confirm.unload_question`), and `panel_trees.prune` lets every panel drop what was unloaded. The panels register with `app/scene/panel_trees.PanelTrees` (`vids`, `held`, `hold` = their setters, `opens` = what an eye opened makes them hold, the path conversions and `moves` for the Statistics view); an eye click is `panel_trees.eye(kind, vid, paths, on)`. The server owns the boxes: a click shows at once in the widget, and every time the server publishes or puts back the selection it bumps `tree_boxes_n`, which every tree watches (`boxesNonce`, tree widget 0.12.10) to read `selected` again — a refused or vetoed tick leaves the list unchanged, and trame does not re-send an unchanged value. The setters below now back the EYE: what they add is taken in, what they drop is let go, nothing is unloaded.

**API.** `expand(ticked, is_leaf, descendants)` — the leaves a ticked set stands for (a leaf is itself, a folder every leaf under it: the widget sends the folder's own path and the cascade is the server's, in every tree). `panel_wells(ticked, wellbore_of)` — the wellbores the log holds after a tick, whatever node was ticked: the log correlates wellbores.

**Who uses it.** `app/boot.py`: `compare_tree_paths` (tick → the selection, a folder standing for the leaves under it), `welllog_tree_wells` (tick → the well in the log, plus the `welllog_dropped__<vid>` set of what the log was told to leave out), `welllog_tree_ticks` (the log tree's SEED — the wells and what the panel draws under them), `_panel_tick_read` (the read those ticks ask for, under the shared confirmation), `panel_tree_eye` / `panel_tree_eyes` (the 3D eye and the paths that may carry one — representations, arrays **and markers**).

**A rewrite is not a gesture (2026-09-13).** Both panel trees are two-way, so every server rewrite of their ticks comes straight back through the tree's own watcher. Boot keeps what it last published per view — `_compare_published` and `_welllog_published`, pruned to the open panels by the `_sync_*_trees` that write them — and reads the echo for what it is. Without that baseline: a folder tick took its leaves in, re-synced, re-entered, posed a SECOND question over the first, and `Cancel` ran the second one's callbacks, so a reader who said no was left with 27 ticked boxes and 27 cards each blaming the file; and `welllog_tree_wells` computed its drops against `selected_paths`, so a log tree seeded with the wellbores alone (the panel's own seed, on a session that already held the wells) read as a reader who had just unticked all 176 read nodes and the panel drew nothing under an empty state saying "no curve read from them yet". `_ask_tick` also refuses a second question while one stands, stepping the newcomer back through its own `on_no` instead of overwriting the standing pair of answers. And the panel is filled by `on_go`, which runs only once the read goes ahead — `_hold` for the log, the view's own for Statistics — so a box that is still asking never stands in front of a panel already holding what it is asking about. `_hold` re-syncs the tree's boxes itself ONLY when the wells did not move: when they did, `_on_welllog_inputs` does it after the read, and writing them in the same flush as the read sent a stale echo — the wells alone — back through the tree's watcher against a baseline the read had already advanced, which dropped all 176 curves the tick had just brought in. The wrappers are `app/views/widgets/{welllog,compare,reconcile}_tree.py`; the state vars are listed in `Engine-Lifecycle-and-State` and in `per_view_state.SUFFIXED_VARS`. Unit: `tests/unit/test_tree_grammar.py`, `tests/unit/test_panel_tree_menus.py`.

### `fespp_on_trame/engine/compare_matrix.py`

**Responsibility.** Pure (no PV/state) primitives for the matrix of the **Statistics** view: the canonical metric list, the sort, the highlight annotations (the sign against the baseline, or the extrema of a block without one), the deltas to the baseline and the distribution profile classification. Operates only on item dicts carrying a `row` of metrics — what `compare_dispatch.matrix` builds. The metric LABELS are client-side, in `widgets/compare/vue-components/src/metrics.js`, and the CSV export in `ComparePanel.vue`.

**Key classes / functions.**
- `_METRIC_KEYS` (canonical order, `Mean (L)` after `Mean (PV)`) — also the whitelist boot filters `ui_compare_visible_metrics` through, so what the view shows is always a subset of these, in this order.
- `SORT_KEYS` — what a column header may sort the block by: `REPRESENTATION` (`"Representation"`, the row's own column: `support_label`, else `rep`), `TOTAL` (`"Total"`, defined + undefined) and the `_METRIC_KEYS`; the `sort` gesture (`app/features/compare_tree`) keeps a key only from this list. `sortable(row)` gives what a row is sorted on: its metrics, its total and its representation's name.
- `sort_items(items, sort_key, sort_asc)` — stable sort by one of those keys: numbers by value, words alphabetically whatever their case; None, an empty word, NaN and anything else sink to the bottom in either direction.
- `highlight_annotations(rows, mode, base_idx=None)` — returns `{metric_key: {row_idx: tag}}`. Modes: `"extrema"` (`'min'`/`'max'`), `"baseline"` (`'pos'`/`'neg'`/`'eq'`, the sign of each row's difference to the row at `base_idx`, the baseline itself `'eq'`). The heatmap mode (a float 0..1 per cell) went on **2026-09-15**: nothing ever asked for it.
- `baseline_deltas(rows, base_idx)` — `{metric_key: {row_idx: {abs, rel}}}`, each row's difference to the baseline row in the metric's unit and in percent of the baseline (`rel` None when the baseline is 0; 0 when the two are the same read's float noise apart, `_delta`); the baseline row has no entry. `highlight_annotations_for_items` / `baseline_deltas_for_items` are the same over `item["row"]`, the baseline found by `item["key"]`. **Since 2026-09-15 the deltas are SHOWN**: `compare_dispatch.deltas_from_rows` → `ui_compare_deltas`, written under each cell of the kind's matrix by the widget (`+0.0123 (+7.1 %)`, the count metrics in full, the quantities by the shared rule). Before, the wrapper computed them into a `_deltas` entry the dispatcher then dropped: a number computed and never shown.
- `profile_tag(skewness, kurtosis)` — classifies `symmetric`/`skewed_right`/`skewed_left`/`heavy_tail` (treats kurtosis as excess, centered on 0); `""` on missing/non-numeric.
- `highlight_annotations_for_items(items, mode, baseline_key=None, normalize=False)` — wrapper that drills into `item["row"]` for metrics; for baseline mode rebuilds the dict by **index** (the row dict lacks the item key) and stashes absolute + relative deltas under the `"_deltas"` sub-key.

**State.** None (pure module).

**Collaborators.** Consumes the rows `compare_dispatch.matrix` builds, and is consumed by that same module (plus boot, for the metric whitelist and the re-sort). No PV, no trame state.

**Gotchas.** Two highlight entry points exist: `highlight_annotations` (operates on flat dicts where metrics are top-level keys) vs `highlight_annotations_for_items` (operates on the wrapper items, drilling into `["row"]`). The wrapper calls the flat version with `baseline_key=None` and then **rebuilds baseline mode from scratch using `base_idx`** — because baseline lookup needs the item key that only the wrapper carries. The kurtosis convention assumption ("treat value as excess, centered on 0") matters: if a pipeline ever returns raw (non-excess) kurtosis, `profile_tag`'s `heavy_tail` threshold would misfire.

### `fespp_on_trame/engine/etp.py`

**Responsibility.** ETP/OSDU connection lifecycle plus a shared `update_data_information` that re-parses the live `vtkDataAssembly` into the engine `Tree` (works for both Collector and ETPConnector). Extracted from `boot.initialize_fespp_engine`.

**Key classes / functions.**
- `connect_to_etp(state, etp_connector, etp_url, data_partition, token, token_type="Bearer", proxy_url=None, proxy_token=None, proxy_token_type="Bearer")` — calls `etp_connector.connect(...)`; on success sets `state.etp_dataspaces = etp_connector.get_dataspaces()`, else `[]`.
- `select_etp_dataspace(etp_connector, dataspace)` — `etp_connector.set_dataspace(dataspace)` when connected.
- `force_etp_refresh(state, etp_connector, collector, tree)` — runs `UpdatePipelineInformation()` **twice with a 0.5s sleep between** (to surface late-arriving ETP entries when the server defers dataspace enumeration), then calls `update_data_information`.

**State.** Writes `etp_dataspaces`. Reads none.

**Collaborators.** `paraview.simple` (imported), `time.sleep`, the `ETPConnector` (`connect`, `is_connected`, `get_dataspaces`, `set_dataspace`, `get_source`), the `collector` (`get_source`), the engine `Tree.set_tree`. Entry points are boot.py closures.

**Gotchas.** `GetLiveAssembly` is the **preferred** getter because after `rebuildAssembly()` (a TreeHierarchyMode change) the live assembly is mutated without re-running RequestData, so the pipeline output's deep copy is stale. `GetAssembly()` exists on the parent class but isn't always wrapped to Python through the override; `GetLiveAssembly` is unique and always wrapped. The double-`UpdatePipelineInformation` + sleep is an empirical workaround for background dataspace enumeration on the ETP server side.

### `fespp_on_trame/engine/vtk_log.py`

**Responsibility.** Capture VTK/ParaView C-level stderr (fd 2, via vtkLogger — invisible to Python `print`/`logging`) and tee it to both docker logs and an in-memory queue the UI surfaces via `state.vtk_log_messages`.

**Key classes / functions.**
- Module state: `_vtk_log_queue` (list), `_vtk_stderr_tee_done` (bool), `_ANSI_RE`, `_VTK_LINE_RE` (parses `(  29.2s) [thread] file.cxx:67  ERR| message` into level tag + text), `_SUPPRESS_PATTERNS` (currently just `"No active view found"`).
- `setup_stderr_tee() -> None` — **idempotent.** Creates an `os.pipe()`, dups the original fd 2 aside, redirects fd 2 to the pipe write end, and starts a daemon `_reader` thread that drains whole lines, strips ANSI, applies `_SUPPRESS_PATTERNS` (suppressing in **both** docker logs and the queue), forwards non-suppressed raw lines (ANSI intact) to the original fd 2, and appends `{text, level}` dicts (level from the `ERR`/`WARN` tag) to `_vtk_log_queue`.
- `capture_vtk_messages(state, max_messages=500)` — context manager that records `start_seq = len(queue)` on entry; in `finally` sleeps `0.05s` (let the reader flush the pipe), slices `queue[start_seq:]`, and appends to `state.vtk_log_messages` (capped to the last `max_messages`). It YIELDS the list of the entries captured by the block (filled when the block ends): a caller diffing `len(state.vtk_log_messages)` saw nothing new once the cap was reached — a failed import after a warning flood had no error to report. `boot.load_epc_file` and the selection load (`_on_selectors`) read that list through `engine.io.read_report`.

**State.** Writes `vtk_log_messages` (in `capture_vtk_messages`).

**Collaborators.** Stdlib only (`os`, `threading`, `re`, `contextlib`, `sys`, `time`). `setup_stderr_tee` is called once at boot (after ParaView init); `capture_vtk_messages` wraps engine blocks whose VTK output should reach the UI log panel.

**Gotchas.** `setup_stderr_tee()` **must run AFTER ParaView init** or startup noise floods the queue. Module-level singletons (`_vtk_log_queue`, the tee thread) are intentional — there is exactly one stderr fd per process, so the queue is sliced by index (`start_seq`) so a single tee thread serves multiple concurrent sessions. The reader buffers and splits on `\n` so the suppression decision is per-line (a raw 1024-byte read may straddle a line boundary). Suppressed lines are dropped from docker logs too — add a narrow `_SUPPRESS_PATTERNS` entry rather than silencing a broad category. The `"No active view found"` suppression specifically covers the window where `stats_dispatch.transient_chain` holds the active view at None.
